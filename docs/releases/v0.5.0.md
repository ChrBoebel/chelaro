# Chelaro v0.5.0 — Explicit Assistant Model Selection

Chelaro `0.5.0` makes the finance assistant's model, reasoning depth, and speed a Chelaro decision
instead of an inherited one, shows what a conversation runs on and what it costs, and repairs
continuing a conversation without restarting the app.

## Behavior change you will notice

Chelaro never sent a model, reasoning effort, or service tier to Codex. Because the assistant runs
against your real Codex home (ADR 0011), Codex resolved all three from your personal
`~/.codex/config.toml`. On a machine configured for coding work — for example
`model = "gpt-5.6-sol"`, `model_reasoning_effort = "high"`, `service_tier = "priority"` — the
finance assistant silently ran on exactly that. None of it was visible in Chelaro, and editing an
unrelated file changed the assistant.

From this release the assistant starts at **GPT-5.5, medium effort, standard tier** and lets you
change all three in the product. If your Codex configuration named a different model, the assistant
will answer differently than before. That is deliberate. Fast Mode is opt-in because Codex describes
its `priority` tier as 1.5x speed at increased usage.

Existing conversations predate the explicit selection. They are backfilled with the new default and
re-bound the next time you continue them.

## User-visible behavior

- Model, reasoning depth, and Fast Mode can be chosen before a conversation starts and stay bound to
  it. Only models whose provider edge was verified are offered; the effort options and the Fast Mode
  switch come from the selected model's own catalog entry.
- The chat header names the model, depth, and Fast Mode the open conversation actually runs on, and
  **Konfiguration ändern** closes the conversation so it can be rebound.
- Token usage, how full the model context window is, and how often Codex condensed the history are
  visible while chatting.
- Continuing a conversation works within one application run. It previously failed with a conflict
  until Chelaro was restarted.
- A rejected action names its reason — missing Codex login, an unavailable model, a running answer —
  instead of always suggesting a retry that could not succeed.
- Answers can be copied, a failed or interrupted question can be resent, and the example questions
  are buttons that fill the input field.

## Security and migration

Model, effort, and service tier travel with every `thread/start` and `thread/resume`. A thread counts
as configured only when Codex echoes back exactly the requested values: the pinned App Server accepts
an unknown model, effort, or tier **without an error** and reports a substituted or `null` value
instead, measured including under `--strict-config`. `model/rerouted` and `model/verification`
abort the turn.

The GPT-5.6 family is not offered. `gpt-5.6-sol` and `gpt-5.6-terra` declare collaboration and
agent-spawning tools at the provider edge that the pinned App Server cannot remove, and `gpt-5.6-luna`
declares `wait`. ADR 0010's stop condition applies to all three. See
[ADR 0014](../decisions/0014-explicit-finance-model-selection.md).

The host's per-epoch identifier ledger now records the role each identifier was seen in. A resumed
provider thread may reattach to its own identifier; the same identifier appearing as a session or
turn identifier is still refused.

Both database paths gain the binding: Alembic revision `20260901_0011` for PostgreSQL and desktop
schema version 5 for the local SQLite database. Both backfill existing rows with
`gpt-5.5 | medium | default`.

Consent is unchanged. The provider, the transferred data categories, and the notice all stay the
same, so no new consent version is required.
